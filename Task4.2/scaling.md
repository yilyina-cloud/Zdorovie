# Стратегия горизонтального масштабирования

Цель — подготовить системы к 50 000 одновременных пользователей
с временем отклика менее одной секунды для 99% запросов.

Выбраны две критичные системы:
- Расписание — поиск слотов и оформление записей; уже возникают блокировки БД.
- CRM — карточки пациентов и результаты анализов; новый мобильный канал увеличит нагрузку на чтение.

| ИТ-система | Реализация горизонтального масштабирования | Ограничение | Описание решения для него |
|---|---|---|---|
| **Расписание** | Запустить несколько экземпляров сервиса за балансировщиком. Не хранить состояние пользовательских операций в памяти отдельного экземпляра. Для PostgreSQL добавить реплики чтения: направлять на них поиск и просмотр слотов. Резервирование, подтверждение и отмену выполнять на основном узле БД. Число экземпляров сервиса увеличивать по нагрузке и времени ответа. | Реплики масштабируют чтение, но не устраняют конкуренцию за запись на основном узле БД. Блокировки популярных слотов могут сохраняться. | Резервировать слот короткой атомарной транзакцией с проверкой доступности и защитой от двойного бронирования. Не удерживать блокировку во время оплаты или вызова LIS. Если основной узел достигает предела, распределить данные и операции по независимым шардам, например по клиникам, сохранив все операции одного слота на одном шарде. |
| **CRM** | Запустить несколько экземпляров REST-сервиса за балансировщиком. Добавить реплики PostgreSQL для чтения карточек и результатов. Обновления из потока LIS → RabbitMQ → backend → CRM направлять на основной узел. Масштабировать обработчики результатов в backend отдельно, ограничивая их параллелизм пропускной способностью CRM. | Реплики могут отставать: после сохранения анализа и отправки пуша пациент рискует получить старые данные. | После пуша запрос содержит идентификатор и ожидаемую версию результата, без медицинских данных. Backend проверяет версию ответа CRM; если реплика ещё не получила обновление, CRM выполняет адресное чтение с основного узла. Реплики с недопустимым отставанием временно исключаются из чтения. |

## Правила согласованности

- Поиск слотов через реплики носит предварительный характер.
  При резервировании доступность обязательно проверяется на основном узле.
- Подтверждённая запись и состояние только что выполненной операции
  читаются с основного узла, чтобы пациент сразу видел актуальный результат.
- Идемпотентность сохраняется при любом количестве экземпляров:
  ключи операций и результаты хранятся в общей БД, а не локальной памяти.
- В CRM остаётся проверка resultId и версии из Task3.1:
  параллельная обработка не создаёт дублей и не заменяет новые результаты старыми.

## Проверка масштабирования

50 000 пользователей не равны 50 000 запросов в секунду.
Для расчёта мощности необходимо определить частоту действий,
долю чтения и записи, объём ответов и распределение нагрузки по клиникам.

Нагрузочный тест воспроизводит поиск слотов, создание записей,
просмотр анализов и одновременное поступление результатов из LIS.
Проверяются p99, частота ошибок, блокировки БД, отставание реплик
и возраст сообщений в очередях.

Количество экземпляров и реплик определяется тестами.
Добавление экземпляров приложения само по себе не гарантирует
целевое время отклика, если ограничением остаётся база данных.
