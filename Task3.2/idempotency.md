# Идемпотентность создания записи

1. Перед отправкой новой операции приложение создаёт UUID и передаёт его в заголовке Idempotency-Key. При повторе того же запроса после тайм-аута используется тот же ключ.

2. Gateway передаёт ключ в backend. Backend связывает его с идентификатором авторизованного пациента и типом операции.

3. В общей БД backend атомарно сохраняются ключ, хеш параметров запроса и новая операция SAGA. Уникальное ограничение на сочетание «пациент + операция + ключ» защищает от одновременных повторных запросов.

4. Если ключ уже существует:
   - при совпадающих параметрах возвращаются тот же operationId и текущее состояние;
   - при других параметрах возвращается 409 Conflict;
   - новая SAGA не запускается.

5. Для каждого изменяющего шага backend формирует постоянный ключ на основе operationId и названия шага. Он используется при всех повторах резервирования, оплаты, подтверждения и компенсации.

6. Зависимые системы должны сохранять результат обработки ключа вместе с бизнес-изменением. Если внешний API не поддерживает идемпотентность, необходимы поиск операции по стабильному идентификатору и сверка статуса. Один адаптер не гарантирует отсутствие двойного списания.

Срок хранения ключей должен покрывать выполнение SAGA, повторные обращения и компенсации. Ключи незавершённых операций не удаляются.

Идемпотентность защищает от повторения одной операции. От бронирования одного слота разными операциями отдельно защищает атомарная проверка доступности в системе расписания.
