# Задание 2. Целевая интеграционная архитектура

Архитектура сохраняет существующие системы и добавляет мобильное приложение, API Gateway, сервис аутентификации и backend. Внутренняя логика backend на контекстной диаграмме не раскрывается.

## Интеграции и выбранные паттерны

| Интеграция | Решение и обоснование |
|---|---|
| Приложение → сервис аутентификации | OIDC, Authorization Code Flow с PKCE. Централизованный вход и выдача токенов без передачи пароля в бизнес-системы. |
| Приложение → Gateway → backend | REST/HTTPS. Gateway проверяет токены и ограничивает запросы. Backend предоставляет единый API и проверяет доступ пациента к конкретным данным. |
| Backend → Расписание | Синхронный REST для получения слотов и управления записью. Идемпотентность предотвращает повторное создание записи, а система расписания защищает слот от одновременного бронирования. |
| Backend → CRM | Синхронный REST для чтения данных пациента и обновления результатов. CRM хранит доступную приложению копию анализов, LIS остаётся их источником. |
| Backend → 1С | Адаптер изолирует изменения формата 1С. Cache-Aside уменьшает число проверок полиса; срок актуальности кэша согласуется с бизнесом. Тайм-аут означает «проверка недоступна», а не «полис действителен» или «недействителен». |
| Backend → платёжный шлюз | REST через адаптер. Идемпотентный платёж и сверка статуса после тайм-аута предотвращают повторное списание. |
| Backend → LIS | Адаптер SOAP/REST для резервирования и отмены сдачи анализов. Наличие этих методов требуется подтвердить; при отсутствии понадобится доработка LIS. |
| LIS → RabbitMQ → backend → CRM | Событийная доставка результатов. Transactional Outbox сохраняет результат и событие в одной транзакции LIS. Повторы и идемпотентная обработка обеспечивают восстановление после сбоя без дублей в CRM. Старый ненадёжный коннектор заменяется этим потоком. |
| Расписание → RabbitMQ → получатели | Publish–Subscribe для подтверждений, переносов и отмен. Outbox обеспечивает надёжную публикацию, а получатели обрабатывают события независимо. |
| Backend → RabbitMQ → Уведомления | Асинхронные события оплаты и доступности анализов. Событие готовности анализа для пациента публикуется после сохранения результата в CRM. |
| Уведомления → провайдеры → пациент / приложение | Доставка СМС, писем и пушей. Пуш не содержит медицинских результатов: приложение получает их через защищённый API. |

## Сочетание архитектурных стилей

- **Сервисный:** существующие системы сохраняют свои функции, backend объединяет их в сценарии приложения.
- **Request–Response:** используется для чтения данных и команд, требующих непосредственного ответа.
- **Событийный:** используется для доставки анализов, изменений записей и уведомлений.

Запись с оплатой и резервированием анализов выполняется как **оркестрируемая SAGA**. Backend хранит состояние операции и запускает компенсации при сбоях: отмену резервов и возврат подтверждённого платежа.

## Условия реализации

- Outbox в LIS и расписании — предлагаемая доработка. Возможность её реализации необходимо подтвердить.
- События доставляются как минимум один раз. Получатели удаляют дубли по идентификатору события и учитывают версию результата.
- Для интеграций применяются тайм-ауты, ограниченные повторы, circuit breaker и сквозная трассировка.
- Существующий RabbitMQ необходимо подготовить к новой нагрузке: обеспечить отказоустойчивость, мониторинг и отдельные очереди для разных получателей.
- Веб-портал сохраняется. Исправления идемпотентности, платежей и доступа должны распространяться и на его сценарии.
- Параметры отказоустойчивости, масштабирования и безопасности уточняются в Task4.
