# API получения записей пациента

Endpoint: GET /api/v1/appointments?status=upcoming&limit=20&offset=0

## Доступ к данным

Приложение передаёт access token в заголовке Authorization: Bearer <access_token>.
Gateway проверяет токен, backend определяет пациента и получает только его записи
из системы расписания. Параметр patientId клиентом не передаётся.

Это соответствует Task2. Незавершённая операция оформления из Task3.2
отслеживается через /operations/{operationId}; в предстоящие записи
попадает подтверждённый приём.

## Фильтрация

По умолчанию status=upcoming: возвращаются подтверждённые записи,
время начала которых позже текущего времени сервера.
Также доступны completed и cancelled.

## Пагинация

Используются limit и offset, как требуется в задании.
По умолчанию возвращается до 20 записей, максимально — 100.
Это предложенные параметры API, а не ограничения из исходного кейса.

Следующая страница запрашивается с offset + limit.
Поле total показывает количество записей после фильтрации.

Сортировка фиксирована: startsAt, затем appointmentId.
При изменении списка между запросами страницы могут смещаться —
это ограничение offset-пагинации. Для небольшого списка записей
одного пациента такой подход прост и достаточен.

## Версионирование

Версия API указана в URL: /api/v1.
Несовместимые изменения выпускаются в /api/v2.
OpenAPI 3.2.0 — версия формата спецификации, а не версия самого API.

В тексте задания указана OpenAPI 3.2, в разделе сдачи — 3.0.
В решении выбрана 3.2.0 согласно основному описанию задания.

## Ответы

- 200 — список записей, включая пустой список.
- 401 — требуется аутентификация.
- 500 — внутренняя ошибка без раскрытия технических деталей.
- 400 — дополнительно предусмотрен для некорректных параметров.

Имена, адреса и идентификаторы в примерах условные.
