# Безопасность мобильного приложения

## Аутентификация и доступ

Используем OpenID Connect поверх OAuth 2.0,
Authorization Code Flow с PKCE (S256).

1. Приложение создаёт случайные code_verifier, state и nonce.
   Из code_verifier вычисляет code_challenge.
2. Открывает страницу сервиса аутентификации в системном браузере.
   Пользователь вводит учётные данные на этой странице.
3. После входа сервис возвращает приложению одноразовый authorization code.
   Приложение проверяет state.
4. Приложение обменивает code и code_verifier на токены.
   Сервис проверяет PKCE и точное совпадение зарегистрированного redirect URI.
5. Приложение проверяет ID token, включая подпись, issuer, audience,
   срок действия и nonce. ID token используется для входа, не для вызова API.
6. Для вызовов API передаётся access token:
   Authorization: Bearer <access_token>.

Предлагаемый срок access token — 10 минут.
Для обновления используется refresh token с ротацией:
каждое обновление выдаёт новый refresh token и аннулирует предыдущий.
Повторное использование старого токена приводит к отзыву связанной сессии.

Токены хранятся в защищённом хранилище ОС.
В мобильное приложение не встраивается client secret.
При выходе refresh token отзывается, локальные токены удаляются.

API Gateway проверяет подпись access token, разрешённый алгоритм,
issuer, audience и срок действия. Для этого решения выбирается JWT access token.
При отсутствии или недействительности токена возвращается 401.

Backend определяет пациента по проверенному контексту пользователя
и проверяет доступ к каждой записи, полису и результату анализа.
Переданный клиентом идентификатор объекта сам по себе не даёт права доступа.

Backend доступен только через разрешённые внутренние соединения.
Gateway удаляет подставленные клиентом заголовки идентичности
и передаёт проверенный контекст по защищённому каналу.

## Rate limiting

Лимиты ниже — стартовые проектные настройки.
Они уточняются нагрузочными тестами и анализом обычного поведения пациентов.

Используется скользящее окно 60 секунд.
Счётчики общие для всех экземпляров API Gateway.

| Тип запроса | Лимит | Действие при превышении |
|---|---|---|
| Публичный поиск врачей — GET /api/v1/doctors | 60 запросов за 60 секунд на IP-адрес. Для авторизованного пользователя дополнительно применяется такой же лимит на учётную запись. | Вернуть 429 Too Many Requests и Retry-After с количеством секунд до разрешённого повтора. Запрос не передавать в backend. |
| Создание записи — POST /api/v1/appointments | 5 запросов за 60 секунд на авторизованного пациента, суммарно со всех его устройств. Повторные запросы с Idempotency-Key также учитываются. | Вернуть 429 Too Many Requests и Retry-After. Не создавать новую операцию SAGA. Уже принятые операции продолжают выполняться. |

Ограничение по IP для публичного поиска учитывает риск общей сети
у нескольких пациентов. При настройке проверяется, что обычные пользователи
не блокируются массово из-за одного адреса.

Приложение не повторяет запрос раньше Retry-After.
После 429 повтор создания записи использует прежний Idempotency-Key,
если это та же операция. Состояние уже принятой операции запрашивается
через GET /api/v1/operations/{operationId}.

Rate limiting ограничивает частоту запросов,
а идемпотентность предотвращает повторное выполнение операции.
Оба механизма необходимы.

## Защита каналов передачи данных

- Все внешние API и страницы входа работают только через HTTPS.
  Используется TLS 1.2 или выше, предпочтительно TLS 1.3.
- Приложение проверяет сертификат сервера и соответствие имени хоста.
  Отключение проверки сертификатов запрещено.
- Между Gateway, backend и внутренними API используется TLS.
  Для Gateway → backend и поддерживающих это сервисов применяется mTLS
  с отдельными сертификатами и проверкой идентичности вызывающего сервиса.
- Соединения с RabbitMQ используют AMQP поверх TLS.
  Каждому сервису выдаются отдельные учётные данные
  и минимальные права на нужные очереди и exchanges.
- Для HTTP-шлюза 1С и legacy-интерфейсов LIS без собственной поддержки TLS
  используется защищённый прокси или туннель.
  Незашифрованный участок допускается только внутри изолированного
  локального сегмента рядом с системой; прямой внешний доступ закрывается.
- Существующая загрузка по FTP заменяется на SFTP/FTPS,
  если оборудование поддерживает такой режим.
  Иначе канал изолируется и защищается туннелем.
- Токены, пароли и медицинские результаты не передаются в URL
  и не записываются в логи. В трассировке используются технические
  идентификаторы операций.
- Пуш содержит только сообщение о событии и необходимые идентификаторы,
  без медицинских результатов. Сами данные приложение получает
  через API после проверки доступа.
- Платёжные реквизиты вводятся в защищённой форме платёжного провайдера
  и не проходят через backend приложения.

## Устранение проблем из Task1

SQL-инъекция устраняется параметризованными запросами к БД,
валидацией входных данных и минимальными правами учётной записи БД.
TLS и API Gateway сами по себе SQL-инъекцию не устраняют.

Для предотвращения доступа к чужим данным выполняется серверная
проверка принадлежности каждого объекта пациенту и ролей сотрудников.
Тестами проверяются подмена идентификаторов и попытки доступа
с чужим, истёкшим или изменённым токеном.

Возможная подмена сессии из SD-007 требует отдельного расследования:
её причина в кейсе не подтверждена.
